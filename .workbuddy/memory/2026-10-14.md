## 修复：「无消耗」拟饵被当成一次性鱼饵扣除

用户反馈：一些标称「无限消耗 / 无消耗」的拟饵，实际钓鱼时会被扣数量。

### 真因
- 鱼饵数据（`core/initial_data.py::BAIT_DATA`）每条最后一个字段是 **`is_consumable`**：
  - 亮片拟饵（bait_id=5）、大师拟饵（bait_id=12）→ `is_consumable = False`（「无消耗，可长期使用」）
  - 其余一次性鱼饵 → `is_consumable = True`
- `is_consumable` 是**真实持久化字段**：`Bait` 模型有（models.py:82）、`baits` 表有列（迁移 003 `is_consumable INTEGER DEFAULT 1`）、
  `_row_to_bait` 用 `Bait(**row)` 读入、`add_bait_template` 写入。可靠。
- **Bug**：`fishing_service.py` 的鱼饵消耗分支**只按 `duration_minutes == 0`** 判定「一次性鱼饵，每次钓鱼扣 1」，
  从未读 `is_consumable`。亮片/大师拟饵的 `duration_minutes` 也是 0，于是每次钓鱼都被 `update_bait_quantity(-1)` 扣到归零。
- `update_bait_quantity` 在 `quantity <= 0` 时会 DELETE 该行，所以无限拟饵被扣到 0 后直接从库存消失。

### 修复（`core/services/fishing_service.py`，鱼饵消耗块）
把原来的「if duration>0 / else 一次性」二分支，重构为四分支，按 `is_consumable` 判定：
1. 模板不存在 → 清除 current_bait_id；
2. `duration_minutes > 0`（限时）→ 过期才清除，且**仅 `is_consumable=True` 才扣库存**；
3. `is_consumable=True`（一次性）→ 每次钓鱼扣 1，库存为 0 则清除；
4. `else`（`is_consumable=False` 无限拟饵）→ **只应用加成、绝不扣库存、不清除**，长期有效。

### 验证
用「读取真实代码块文本 → dedent → exec + mock 对象」的方式跑了 6 类场景，全绿：
无限拟饵(不扣/不清除) / 一次性有库存(扣1) / 一次性无库存(清除不扣) / 限时未过期(不扣) /
限时已过期可消耗(扣1+清除) / 模板缺失(清除)。`ast.parse` 语法通过。

## 修复：官方 Bot 下状态页个人 QQ 头像获取失败

用户反馈：状态（/状态）里个人 QQ 头像拉取失败，怀疑又是官方 Bot 用 userid(openid) 而非 QQ 号导致。

### 真因
- `draw/utils.py::get_user_avatar(user_id, ...)` 直接把 `user_id` 拼进 QQ 头像 URL：
  `https://q4.qlogo.cn/headimg_dl?dst_uin={user_id}&spec=640`。
- 官方 Bot(qq_official) 下 `user_id` 是 openid（字母数字串，如 `nhB9vRr...`），**不是 QQ 号**，该 URL 必然请求失败；
  原代码虽 `return None` 不崩，但每次都刷一条 `头像下载失败` warning。
- 该函数在 `draw/state.py`(状态)、`draw/backpack.py`(背包)、`draw/pokedex.py`(图鉴) 三处被调用，一处修复全覆盖。
- 调用方本就是「取不到头像就不画」，所以正确做法是**不发起必败请求**，而非强行渲染。

### 修复（`draw/utils.py`）
拉取前加判定：`user_id.isdigit() and 5 <= len(user_id) <= 12` 才视为 QQ 号并发请求；
否则 `logger.debug(...)` 后 `return None`，**静默跳过、不报错不刷 warning**。
- NapCat(aiocqhttp) 等纯数字 QQ 号（5~12 位）仍正常拉头像；
- 官方 Bot openid / 其它非 QQ 数字（如 13 位）均跳过。
- 已用 `ast.parse` 语法检查 + 6 类 user_id 分支测试（NapCat号/老号/官方openid/含数字openid/13位数字/字母数字）验证。

- README「⚠️ 账号体系变化（重要）」段新增头像说明；CHANGELOG 新增 v2.4.9；metadata.yaml 2.4.8 → 2.4.9（三处同步）。
- 提交：fix(compat): 官方Bot下头像按QQ号判断、非QQ号静默跳过。

## 增强：官方 Bot 也能显示头像（按 openid 拉取）

用户追问「官方Bot不能获取qq头像吗？」并确认要接。结论：官方 Bot 拿不到「QQ 号头像」（openid 与 QQ 号无映射），
但官方接口 `GET /v2/users/{openid}` 返回的资料含 `avatar` 字段（官方头像 URL），可以取到 openid 维度的头像。

### 实现（`draw/utils.py`）
- `get_user_avatar` 新增 `event=None` 参数。缓存未命中时：
  - `user_id` 像 QQ 号 → qlogo（同前）；
  - 否则若 `event` 非 None → 调 `_resolve_official_avatar(event)` 取官方头像 URL；
  - 都没有 → debug 日志后返回 None（不报错）。
- `_resolve_official_avatar(event)`：仅当 `event.message_obj.raw_message` 是 botpy `GroupMessage`/`C2CMessage`
  （官方 Bot 上下文）时，用 `event.bot.api._http.request(Route("GET","/v2/users/{openid}", openid=...))` 取资料；
  其它平台/缺 bot/异常 → 返回 None。复用键盘发送的 botpy 原生 HTTP 路由写法。
- `_extract_avatar_from_userinfo(data)`：兼容 `avatar` / `user.avatar` / `data.*` 多种返回结构。
- 24h 缓存：命中则不打接口；QQ 号场景下载失败仍为 warning，openid 场景降级 debug。

### 透传
- `draw/state.py` `draw_state_image` / `draw/backpack.py` `draw_backpack_image`(+`_draw_backpack_image_impl`) / `draw/pokedex.py` `draw_pokedex` 均加 `event=None`，并透传 `event=event` 给 `get_user_avatar`。
- `handlers/common_handlers.py`(状态) / `inventory_handlers.py`(背包) / `fishing_handlers.py`(图鉴) 调用绘图时传入 `event=event`。

### 验证
- `py_compile` 通过；单测（mock botpy + aiohttp）覆盖：官方群/C2C 解析出 thirdqq 头像 URL、非官方原始消息不发请求、
  无 bot→None、官方 openid 完整下载渲染成功、event=None 无缓存→None、数字QQ号缓存→图像。`ALL AVATAR TESTS PASSED`。

### 同步

## 修复：擦弹许可证回执「剩余 2 次」被误读为「只补 2 次」

用户贴出原文：`成功使用了 3 个【擦弹许可证】！🎫 你获得 3 次额外擦弹机会。今天剩余擦弹次数：2 次 (4/6)`。
证实：数值无误——本次获得确为 3（与实际一致）；「剩余 2」是因为当天已擦 4 次（上限 6 → 剩 2）。
用户把末尾「剩余 2 次」误读成「只补 2 次」。原回执把「获得」与「剩余」挤在一行所致。

### 修复（`core/services/item_effects/add_wipe_bomb_attempts_effect.py`）
回执改为三段式：
`🎫 获得 +{total_attempts_to_add} 次额外擦弹机会（今日擦弹加成累计 {extra_attempts_after_update} 次）。\n今天剩余擦弹次数：{remaining_today} 次（已用 {used_attempts_today} / 上限 {total_max_attempts}）`
- 「获得 +N」单列醒目；剩余明确标注「已用 A / 上限 B」。
- 数值逻辑未变（获得=模板amount×数量；累计=buff存量；剩余=上限−当天已用），仅优化表述。
- 单测核验：3 张(已用4)→「获得 +3（累计 3）。剩余 2（已用 4 / 上限 6）」；单张→「获得 +1（累计 1）。剩余 4（已用 0 / 上限 4）」。
