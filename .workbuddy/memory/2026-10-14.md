## 修复：「无消耗」拟饵被当成一次性鱼饵扣除

用户反馈：一些标称「无限消耗 / 无消耗」的拟饵，实际钓鱼时会被扣数量。

### 真因
- 鱼饵数据（`core/initial_data.py::BAIT_DATA`）每条最后一个字段是 **`is_consumable`**：
  - 亮片拟饵（bait_id=5）、大师拟饵（bait_id=12）→ `is_consumable = False`（「无消耗，可长期使用」）
  - 其余一次性鱼饵 → `is_consumable = True`
- `is_consumable` 是**真实持久化字段**：`Bait` 模型有（models.py:82）、`baits` 表有列（迁移 003 `is_consumable INTEGER DEFAULT 1`）、
  `_row_to_bait` 用 `Bait(**row)` 读入、`add_bait_template` 写入。可靠。
- **Bug**：`fishing_service.py` 的鱼饵消耗分支**只按 `duration_minutes == 0`** 判定「一次性鱼饵，每次钓鱼扣 1」，
  从未读 `is_consumable`。亮片/大师拟饵的 `duration_minutes` 也是 0，于是每次钓鱼都被 `update_bait_quantity(-1)` 扣到归零。
- `update_bait_quantity` 在 `quantity <= 0` 时会 DELETE 该行，所以无限拟饵被扣到 0 后直接从库存消失。

### 修复（`core/services/fishing_service.py`，鱼饵消耗块）
把原来的「if duration>0 / else 一次性」二分支，重构为四分支，按 `is_consumable` 判定：
1. 模板不存在 → 清除 current_bait_id；
2. `duration_minutes > 0`（限时）→ 过期才清除，且**仅 `is_consumable=True` 才扣库存**；
3. `is_consumable=True`（一次性）→ 每次钓鱼扣 1，库存为 0 则清除；
4. `else`（`is_consumable=False` 无限拟饵）→ **只应用加成、绝不扣库存、不清除**，长期有效。

### 验证
用「读取真实代码块文本 → dedent → exec + mock 对象」的方式跑了 6 类场景，全绿：
无限拟饵(不扣/不清除) / 一次性有库存(扣1) / 一次性无库存(清除不扣) / 限时未过期(不扣) /
限时已过期可消耗(扣1+清除) / 模板缺失(清除)。`ast.parse` 语法通过。

## 修复：官方 Bot 下状态页个人 QQ 头像获取失败

用户反馈：状态（/状态）里个人 QQ 头像拉取失败，怀疑又是官方 Bot 用 userid(openid) 而非 QQ 号导致。

- `draw/utils.py::get_user_avatar(user_id, ...)` 直接把 `user_id` 拼进 QQ 头像 URL：
  `https://q4.qlogo.cn/headimg_dl?dst_uin={user_id}&spec=640`。
- 官方 Bot(qq_official) 下 `user_id` 是 openid（字母数字串，如 `nhB9vRr...`），**不是 QQ 号**，该 URL 必然请求失败；
  原代码虽 `return None` 不崩，但每次都刷一条 `头像下载失败` warning。
- 该函数在 `draw/state.py`(状态)、`draw/backpack.py`(背包)、`draw/pokedex.py`(图鉴) 三处被调用，一处修复全覆盖。
- 调用方本就是「取不到头像就不画」，所以正确做法是**不发起必败请求**，而非强行渲染。

### 修复（`draw/utils.py`）
拉取前加判定：`user_id.isdigit() and 5 <= len(user_id) <= 12` 才视为 QQ 号并发请求；
否则 `logger.debug(...)` 后 `return None`，**静默跳过、不报错不刷 warning**。
- NapCat(aiocqhttp) 等纯数字 QQ 号（5~12 位）仍正常拉头像；
- 官方 Bot openid / 其它非 QQ 数字（如 13 位）均跳过。
- 已用 `ast.parse` 语法检查 + 6 类 user_id 分支测试（NapCat号/老号/官方openid/含数字openid/13位数字/字母数字）验证。

## 修复：擦弹许可证回执「上限」漏算阶级加成（v2.4.12）

用户坚持「加 3 张应剩 ≥3」，但回执显示「剩余 2（已用 4 / 上限 6）」。经逐行排查，定位到**真实 bug**：
v2.4.11 的回执「上限」只算 `基础 + buff`，**漏掉了阶级系统的每日擦弹加成** `wipe_bomb_bonus`（各阶级 +1~+8，config_defaults.py:448-460）。

### 真因
- `/擦弹` 执行（`game_mechanics_service.get_wipe_bomb_max_attempts`，:255/:282）与状态图（`draw/state.py:685`）的上限都含 `基础 + buff + 阶级加成`；

- 有阶级加成的玩家：回执上限比实际可擦次数小、剩余被少算（如基础3+许可3+阶级1，回执显示上限6、剩2，真实可擦上限7、剩3）。
- 用户「我加3应该剩≥3」的直觉是对的——因为真实剩余是 3，回执少算了 1（正好是阶级加成）。

### 排查中已排除的「计数 bug」假设
- `perform_wipe_bomb` 是唯一写入点，每次只 +1 字段并写 1 条 `wipe_bomb_log`（锁步）；被拦截的超上限擦弹在写日志前 return，不写日志 → 字段与日志不会脱节。
- 通用日志 `add_log` 写 `contribution_amount=0`，而 `get_wipe_bomb_log_count_today` 过滤 `>0` → 不计入。
- `get_today()`（utils.py:11）与日志查询都用 UTC+8 → 无跨天时区错位。
- `perform_wipe_bomb` 在 `gacha_handlers.py:308` 仅被 `/擦弹` 调一次 → 无重复调用。
- 配套诊断脚本 `diagnose_wipe.py`（仓库根，一次性）：`python diagnose_wipe.py <fish.db> [user_id]` 列出今日 `wipe_bomb_log` 逐条时间戳 + `users.wipe_bomb_attempts_today` + 当前 buff，用于确认「已用」是否真实。已用假库验证可用。

## 新增：群聊回复 @ 发送方（v2.4.17，仅关键回复）

用户问「回复消息能不能 @ 消息发送方」。结论：@ 提及可行（官方 Bot 用 `<@!openid>` 文本、NapCat 用 `[CQ:at,qq=...]`）；但「回复引用原消息」(Reply 段) 在 qq_official 下平台不支持（适配器 `_post_send` 只认 Plain/Image/Record，Reply 被丢弃），故只做 @ 提及。

### 实现
- 新增 `utils.format_mention_reply(event, text)`：群聊（`event.get_group_id()` 非空）下在文本前拼发送方 @；私聊原样返回；发送方取 `event.get_sender_id()`（官方 Bot=openid 用 `<@!openid>`，NapCat=纯数字用 `[CQ:at,qq=...]`）；文本为空时只返回提及串本身（图片回复前单独 @）。defensive：缺方法/异常 → 原样。
- 应用范围（用户选「仅关键回复」）：
  - 文本：钓鱼结果 `fishing_handlers.fish`、签到 `common_handlers.sign_in`、面板纯文本降级 + `/选` 结果 `main.py::quick_menu`/`quick_select`。
  - 图片：状态图 `common_handlers.state`、背包图 `inventory_handlers.user_backpack`——图片前先 `yield event.plain_result(mention)` 再 `image_result`。
- 不扩展到全部回复（避免大规模替换；报错提示没必要 @）。

## 修复：@ 必须在同一条消息 + 头像根因（v2.4.18）

用户实测 v2.4.17 后明确三点不满：① @ 要放在「同一条消息」里，不能拆两条；② 有的消息 @ 有的没有，「全是 bug」；
③「头像还是没出来」；④ 已停用 NapCat，只用官方 QQ 机器人。

### 真因
1. **@ 拆两条**：v2.4.17 里状态图/背包图图片回复是 `yield event.plain_result(mention)` 后 `yield event.image_result(path)`，
   @ 作为独立空文本消息先发，紧接着才是图片——群聊下表现为「一条只有 @ 的孤消息 + 一条图」，用户感知为不一致 bug。
2. **头像两个真因（比 v2.4.15 的「信号」更底层）**：
   - **导入路径写错**：`draw/utils.py::_resolve_official_avatar` 里写的是 `from .core.qq_official import ...`，
     但 `core` 在插件**顶层包**，正确应是 `from ..core.qq_official import ...`。运行期抛 `ModuleNotFoundError`，
     被 `get_user_avatar` 的 `try/except` 静默吞掉 → 头像永远走不到官方接口（这才是「头像还是没出来」的真正主因，
     与 v2.4.15 修的「检测信号」无关，检测早就能命中，只是命中之后的取头像代码第一行就 import 崩了）。
   - **群 member openid 是群作用域**：官方 Bot 群聊 `event.get_sender_id()` 返回群成员 openid，旧代码只用
     C2C 接口 `GET /v2/users/{openid}`（群成员 openid 用该接口必然 404）。必须用群成员接口
     `GET /v2/groups/{group_openid}/members/{member_openid}`。

### 修复
- **@ 同条消息**：`common_handlers.state` / `inventory_handlers.user_backpack` / `fishing_handlers.pokedex` 三处个人图片回复，

- 文本回复（钓鱼结果/签到/面板/`/选`）本就用 `format_mention_reply` 直接包 @，行为一致 → 全回复统一。

## 修复：chain_result 传 MessageChain 崩溃（v2.4.19）

用户部署 v2.4.18 后报运行期崩溃：
`TypeError: object of type 'MessageChain' has no len()`，位于 AstrBot `result_decorate/stage.py:200` 的 `if len(result.chain) > 0:`。

### 真因
- v2.4.18 把状态/背包/图鉴图片回复写成 `event.chain_result(MessageChain().message(mention).file_image(path))`。
- AstrBot 的 `event.chain_result(chain)` 把入参**原样**存为 `result.chain`，装饰阶段对 `result.chain` 调 `len()`。
  `chain` 按规定应是 **消息组件列表**（`List[BaseMessageComponent]`），而我传了 `MessageChain` 对象——它没有 `__len__`，
  于是 `TypeError`。`MessageChain` 只是构造器（`.message()`/`.file_image()` 把组件塞进内部 `.chain` 列表），不是列表本身。
- `main.py` 里 `MessageChain().file_image(...)` 走的是 `context.send_message(umo, message_chain)` 低层接口，该接口接受
  `MessageChain`，不受影响——崩溃只发生在命令 `yield event.chain_result(...)` 这一路径。

### 修复（三个 handler）
- `common_handlers.state` / `inventory_handlers.user_backpack` / `fishing_handlers.pokedex` 改为列表形式：
  `event.chain_result([Plain(_mention), Image(file_path=path)])`（私聊 `_mention` 为空则退化为 `image_result`）。
- 顶部导入由 `from astrbot.api.event import ..., MessageChain` 改为 `from astrbot.api.message_components import Plain, Image`。
- `format_mention_reply(event, "")` 在群聊官方 Bot 下返回 `<@!openid>`，`Plain(...)` 渲染方式与文本回复一致（已验证文本 @ 正常）。

### 验证
- `py_compile` 三个 handler 通过（修了一处 initial 过缩进 IndentationError）。
