## 项目结构梳理（迭代开发前的基线调研）

用户要求先梳理 astrbot_plugin_fishing 现状再迭代需求。已完成全库只读探索，结论沉淀如下。

### 架构
- 分层：main.py(组合根/116条指令注册) → handlers/(11文件表现层) → core/services/(20) → core/repositories/(12) → SQLite 单文件 `{data_dir}/fish.db`
- 存储：WAL 模式，40 张表，41 个迁移（001-040），迁移命名约定 `^\d{3}_`，`core/database/migrations/`
- 静态数值种子库：`core/initial_data.py`（FISH_DATA/BAIT_DATA/ROD_DATA/GACHA_POOL/ITEM_DATA 等）
- 领域模型：`core/domain/models.py`，35 个纯 dataclass，**全项目无 Enum**

### 关键扩展点（复用优先）
1. `core/services/fishing_zone_service.py` — 策略模式，新增区域继承 `FishingZoneStrategy` 即可
2. `core/services/item_effects/` — 插件式道具效果，`EffectManager.discover_and_register()` 自动发现
3. `core/achievements/` — `pkgutil` 自动发现成就类
4. `handlers/*.py` + `main.py` 加 `@filter.command` 转发（handler 内无装饰器）
5. `core/database/migrations/0XX_*.py` — 加迁移即自动生效

### 已知技术债（迭代时需注意，勿重复踩坑）
- `main.py:289` 和 `core/database/migration.py:57` 硬编码包路径 `data.plugins.astrbot_plugin_fishing...`
- `handlers/market_handlers.py` 的 `shop()` 单函数约 400 行（102-510）
- 36进制短码有三套重复实现（market_handlers / exchange_handlers）
- `draw/` 中 `draw_rounded_rectangle` 重复4处、`format_rarity_display` 重复3处
- `requirements.txt` 缺 Pillow 与 aiohttp（靠宿主环境带入）
- `tests/` 无 conftest.py，两个测试文件导入路径策略冲突，pytest 难以一次跑通
- `gacha_service.py` 概率展示 `"probability": 1.0 + round(...)` 疑似多加了 1.0
- `game_mechanics_service.py:411` 硬编码向 `http://veyu.me/api/record` 上报数据

### 数值现状（关键）
- 钓鱼基础成功率 0.7（`fishing_service.py:144`），CD 默认 180s，成本取 `zone.fishing_cost`（默认 10）
- 高品质触发用 log2 对数压缩，上限 `quality_bonus_max_chance`=0.35
- 稀有度权重转移：1-3星扣减转移到4-5星，6+不变，boost 上限 0.8
- 区域配额：zone1=50 / zone2=2000 / zone3=500 尾稀有鱼/天
- 税收：起征点 100万，步长 10万，每步 +1%，上限 20%，下限 0.1%
- 鱼塘容量阶梯：480→999(5万)→9999(50万)→99999(5000万)→999999(50亿)
- 精炼上限 10 级，每级加成按稀有度递减（≤3星15% → 7星+3%）

### 状态结论
- 无「钓鱼会话」概念：一次 /钓鱼 = 一次同步事务，无抛竿/咬钩多阶段状态机
- 玩家状态纯数据库，无内存缓存；并发靠 SQLite WAL + timeout=30s，`go_fish()` 无乐观锁
- 骰宝房间是纯内存态，进程重启丢失在途赌局

状态：等待用户提出具体需求细节。

## 配置体系梳理与补齐（需求：后台下发配置项盘点 + 容错统一）

- `core/config_defaults.py` —— 配置默认值单一事实来源。提供 `safe_get` / `safe_get_nested` /

  以及 `build_game_config(config)` 统一装配入口。**后续新增配置项请先加到本文件的 DEFAULT_* 常量里。**

3. **卡池 3「每日补给池」物品为空** —— 已在 GACHA_POOL_ITEMS 中补齐，现 5 件物品。

   `pond_upgrades`/`wheel_of_fate` 此前 Service 一直在读但 schema 从未下发，已全部补齐。
6. **`exchange.commodities` 死配置** —— exchange_price_service 读取但 schema 无此键，已补。
7. **`sell_prices.by_rarity_6~10`** —— main.py 读取但 schema 只到 5，已补 6~10 星。
8. **硬编码包路径 `data.plugins.astrbot_plugin_fishing`** —— migration.py 与 main.py 的
   effect_manager 都硬编码，改插件名/换安装方式即崩。已改为按文件路径动态加载 + 传入包对象。
9. **抽卡概率显示 bug** —— `gacha_service` 的 `"probability": 1.0 + round(p,4)` 多加了 1.0。
10. **`shop()` 渲染 `e["costs"]` 硬取** —— 单个脏数据会 KeyError 崩溃，已改防御性跳过。

## 数值经济模型设计与落地（第二轮：把数值配好）

用户澄清需求为「配置商店等等一系列的具体数值」，而非做配置管理系统。
先做经济诊断再改数值，以下为实测数据与最终设定。

### 实测的经济基线（110 种鱼 / 288 次每日上限）
| 稀有度 | 种数 | 价值区间 | 中位价值 | 区域1期望 | 区域2期望 | 区域3期望 |
|---|---|---|---|---|---|---|
| 1星 | 19 | 0-25 | 11 | 60% | 40% | 30% |
| 2星 | 24 | 35-88 | 60 | 30% | 30% | 20% |
| 3星 | 23 | 95-350 | 180 | 8% | 20% | 20% |
| 4星 | 20 | 100-1500 | 850 | 2% | 9% | 20% |
| 5星 | 15 | 800-30000 | 10000 | 0 | 1% | 10% |
| 6-8星 | 9 | 45000-100万 | — | 0 | 0 | 0 |
区域单次期望鱼值（×0.7 成功率）：区域1≈39 / 区域2≈175 / 区域3≈960 金币

### 发现并修复的 5 个数值失衡
1. **精炼倍率指数爆炸**：原 1.0→660，7星满级售价 3.3 亿，击穿整个经济体系。
   改为相邻级固定 ×1.5，10 级累计 **38.4 倍**，7星满级 192 万，与税收阈值同量级。
2. **精炼成本倒挂**：原 low(<=4)=0.25 单一档位，导致 3 星总费(889万) > 5星(533万)。
   改为 6 档细分，实测总费用单调递增：1-2星 378万 / 3星 567万 / 4星 793万 /
   5星 1133万 / 6星 1511万 / 7星+ 1890万。
3. **区域配额倒挂**：原 50/2000/500，区域2 是区域1 的 40 倍且高于区域3。
   改为 **50/200/100**，形成「区域1 稀缺严控、区域2 常规、区域3 高价值低频」的差异。
4. **装备定价与加成倒挂**：星辰钓者(4星)加成强度是海神之赐(5星)的 60%，定价却是 30%。
   改为 4星=300 / 5星=900；渔夫戒指金币加成 1.10→1.25 并明确定位为「稳健财富流」。
5. **商店星石定价锚点缺失**：按「签到 1 星石/天 + 活动补充」重新锚定，
   目标 2星≈7天 / 3星≈14天 / 4星≈30天 / 5星≈90天。

### 关键设计原则（后续调数值请遵循）
- **精炼倍率**：相邻级固定比例（当前 ×1.5），不要用可调指数——玩家能感知「每级涨多少」。
- **费用单调性**：同稀有度下 1→10 级总费用必须随星级单调递增，否则低星反而更贵。
- **配额分档**：区域越难配额越宽松，但高价值区域配额可更低（高价值低频设计）。
- **星石定价锚点**：星石产出≈1/天（签到）+ 红包/活动，顶级装备定在 90 天量级。
- **钓鱼始终正收益**：回本次数应 < 1，放置游戏不能让人亏钱。

## 第四轮：死道具深度排查与机制激活

用户要求「再看看有没有什么死道具，结合商店、区域、钓鱼逻辑赋予用途」。
这次不只看「有无产出途径」，而是逐个验证 **effect 是否真的生效**。

### 发现并修复的 4 个问题

**① 驱灵香（道具17）— 使用入口隐形陷阱**
- `use_item` 对 `is_consumable=False` 的道具直接拒绝，effect 根本走不到
- 即使走到，effect 也返回「请使用 /驱灵 @目标」的错误提示
- 玩家花 6 万金币买到道具，第一次用就报错，无任何提前告知
- **修复**：`inventory_service.use_item` 在「非消耗品拒绝」之前先问effect 要不要给指引；
  effect 改为返回带道具名的三行明确指引。实测输出：
  `【驱灵香】需要指定目标才能使用。/ 正确用法：/驱灵 @目标用户`

**② 幸运药水（道具2）— 加成可无限叠加（数值漏洞）**
- `payload.multiplier` 每次使用直接覆盖写入 buff，**不是叠加也不是封顶**
- 60 星石/个，玩家囤 16 瓶即可把 rare_chance 推到 0.8 以上，
  绕过 `fishing.rare_chance_max_boost=0.8` 的封顶防线
- **修复**：改为累加并封顶（`MAX_BOOST_MULTIPLIER = 0.8`，与 fishing 侧一致），
  时长仍可叠加（续期）。实测连用30 次后 multiplier 恰为 0.8，提示「（已达上限）」

**③ 前往神秘海域的通行证（道具5）— 真正的死道具**
- 机制完整（`fishing_service.py:764-787` 切换区域自动消耗 + 每日检查缺道具传送），
  但迁移 015 创建的三个区域**全部requires_pass=0**，道具永远不会被消耗
- **修复**：新增迁移 043，创建区域4「无尽深渊」
  （requires_pass=1, required_item_id=5, 费用500金币, 配额30/天,
  分布[0.05,0.10,0.20,0.25,0.25,0.15] 集中5-6星）

## 第六轮：装备效果与出货率失衡修复

用户指出「装备效果和钓鱼出货率不合理」。这轮深挖装备加成的实际作用点，
找到 1 个根本 BUG + 3 个平衡问题。

### ① 根本 BUG：coins_chance 是完全无效的属性
- `core/utils.get_fish_template` 原实现：`weight = base_value × (1 + coins_chance)`
- **给所有候选鱼乘同一个常数 → 权重比例完全不变 → 抽样分布不变**
- 20 万次蒙特卡洛验证：cc=0 与 cc=0.5 的 5 星均值 16740 vs 16726（差异 0.06%，纯噪声）
- 受影响的无效属性：渔夫的戒指、丰收号角、海洋之心、价值连城饵
- **修复**：改为幂指数加权 `weight = value ** (1 + coins_chance)`，
  加钳制 `coins_chance ∈ [0, 2]` + OverflowError 线性兜底
- 实测生效：cc=0→16740，cc=0.25→17783，cc=0.5→18759，cc=1.0→20517

### ② 6+ 星鱼完全不吃装备
- `_apply_rare_chance_to_distribution` 的步骤3 原本注释「6+星完全不参与计算」
- 实测无尽深渊 6星+ 概率：裸装 4.000% → 满配 4.000%（零变化）
- **修复**：新增低敏感度加成 `6星+ × (1 + boost × 0.35)`，
  并加**绝对占比封顶 12%** 保证顶级鱼不贬值
- 实测：深海峡谷 0.300%→0.348%，传说之海 1.200%→1.395%，无尽深渊 4.000%→4.628%（均 1.16×）

### ③ 品质加成是鸡肋属性（仅 4.6%）
- 原压缩系数 `max_quality_chance / 2 = 0.175`，满配品质 ×1.44 仅得 4.6% 高品质概率
- 相比 rare_chance 的 4倍收益几乎可忽略，玩家没动力买非稀有向装备
- **修复**：压缩系数改为可配置 `fishing.quality_chance_scale`（默认 0.5）
- 满配 ×1.44 → 高品质概率从 4.6% 提升到 **26~30%**

### ④ 稀有加成封顶 0.8 让精炼 9~10 级零收益
- 满配稀有可达 0.92（鱼竿0.15 + 饰品0.05 + 10级精炼0.72）
- 但 `rare_chance_max_boost` 上限 0.8 → 9级(0.84)、10级(0.92) 全被截断
- **修复**：上限 0.8 → **1.0**（config_defaults / fishing_service / schema 三处同步）
- 实测满配合计从 897 → 1020（区域1），稀有加成 0.92 完整生效

### 重要教训（数值设计）
1. **加权随机中「给所有候选项乘同一常数」是无效操作** —— 等比缩放不改变分布。
   任何 `weight × k` 形式的加成都要先问一句：k 对所有候选项相同吗？
2. **封顶值必须 ≥ 系统能达到的最大值**，否则高投入部分零收益。
   本例封顶 0.8 < 满配 0.92，直接让精炼 8~10 级失去意义。
3. **属性强度要量化对比**，不能凭感觉。本例用「单项启用 vs 裸装」的差值
   来测各属性贡献，发现 rare 独占 90%。
4. `calculate_after_refine` 的精炼等级是 `refine_level - 1`（10级只算9级加成），
   分析时别写成 `0.08 × 9 × 9`（我第一次就犯了这个错）。

**① 税收阶梯断层（最严重）**
旧设定：起征100万 / 步长10万涨1% / 上限20%
| 持有额 | 税率 | 税额 |
|---|---|---|
| 1,000,000 | 0.1% | 1,000 |
| 1,100,000 | **1.1%** | 12,100 |
| 3,000,000 | **20.0%（封顶）** | 600,000 |
| 5,000,000 | 20.0% | 1,000,000 |
三个致命问题：
1. 阶梯太陡：0.1%→20%仅 20 个台阶，持有 300 万即封顶
2. 起征点过低：区域3日均产出 40 万，持有刚过100万就重税，高效玩家 2~3 天积累被吃光
3. **惩罚正确行为**：出售7星10级装备（192万）要交38万税，实质是装备定价的1.8倍成本

新设定：起征 **1000万** / 步长 **500万**涨1% / 上限 **10%**
| 持有额 | 税率 | 税额 |
|---|---|---|
| 5,000,000 | 0.1% | 5,000（几乎不受影响） |
| 12,000,000 | 0.1% | 12,000 |
| 30,000,000 | 4.1% | 1,230,000 |
| 100,000,000 | 10.0% | 10,000,000 |
- 持有 <1000万（绝大多数玩家）完全免税
- 顶级装备 192 万远低于起征点，出售不受惩罚
- 仅超级大亨承担 10% 重税，作为通胀回收的最后闸门

**关键认知修正**：税收是**存量税**不是日流量税，
判断标准应是「税额/日产出」的相对比例而非绝对值。

**② 鱼塘扩容费用与容量脱钩**
旧设定 480→999(5万)→9999(50万)→99999(5000万)→999999(50亿)
- 容量每档涨 10x，费用却涨 10x/100x/100x
- 480 容量仅 **1.1 天**就满（518条/天），新手第一周就鱼塘爆满
- 末档 50 亿需刷 3.5 万次，完全不可达

新设定（按每日 518 条渔获设计，每档对应一个游戏阶段）：
| 区间 | 费用 | 涨幅 | 可积攒 |
|---|---|---|---|
| 480 → 2,000 | 5万 | — | 4 天 |
| 2,000 → 20,000 | 40万 | 8x | 39 天 |
| 20,000 → 200,000 | 500万 | 12x | 386 天 |
| 200,000 → 1,000,000 | 6000万 | 12x | 收藏级 |
费用涨幅（8x/12x/12x）与容量涨幅（10x）已同阶。

## 第九轮：修复 schema 导致的插件加载失败

用户报 AstrBot 加载插件报错：`加载插件「Fishing Another!」时出现问题，原因：'items'`。

### 根因
AstrBot 解析 `_conf_schema.json` 时，对每个 `"type": "object"` 的节点**直接访问
`node["items"]`**，缺失即抛 `KeyError: 'items'`。

我在前几轮新增配置时，为了「让运营能整体替换字典」，写了这种形式：
```json
"refine": {
  "items": {
    "costs": { "type": "object", "default": {"1": 10000, "2": 30000}, "description": "..." }
  }
}
```
`default` 直接给了整个字典而没有 `items` —— 违反schema 规范。

### 违规项共 12 处
- signin.consecutive_bonuses
- pond_upgrades
- refine.costs / cost_multipliers / success_rates / destruction_chances / bonus_per_level
- wheel_of_fate.levels
- exchange.commodities.{dried_fish, fish_roe, fish_oil}（第二层嵌套）

### 修复方式
按 AstrBot 规范把「自由键值对」显式展开为 `items` 结构：
- 数值字典 → `items: {"1": {"type":"int","default":10000,"description":...}}`
- 结构字典（levels / pond_upgrades）→ `items: {"1": {"type":"object","items":{"from":...}}}`
- 移除原`default`（object 型节点的默认值由 items 中各子项的 default 汇总而来）

### 正确的 schema 范式（务必遵循）
```json
// ✅ 正确：显式列出每个键
"volatility": {
  "type": "object",
  "items": {
    "dried_fish": { "type": "float", "default": 0.08, "description": "..." }
  }
}
// ❌ 错误：没有 items，插件直接加载失败
"costs": { "type": "object", "default": {"1":10000}, "description": "..." }
```

### 验证方法（已沉淀）
写脚本严格模拟 AstrBot 行为：遍历所有 `type=="object"` 的节点，
断言存在 `items`，并递归生成默认配置喂给 `build_game_config()`。
最终结果：17 配置块 / 51 个 object 项全部合规，
schema 默认值与 `build_game_config({})` 双路径均能正常装配。

### 教训
1. **写 `_conf_schema.json` 时，`type: "object"` 必须配 `items`，不能用 `default` 整体替代**。
   校验 JSON 语法通过 ≠ 符合 schema 语义，必须模拟框架的解析逻辑来验证。
2. 迭代中新增配置块后，应立即跑一次「模拟框架解析」的校验脚本，
   否则要到用户安装插件时才会暴露。
